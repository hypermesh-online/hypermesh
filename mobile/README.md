# HyperMesh Mobile (Phase C.4)

Native iOS + Android shells. The phone is **not a HyperMesh node**. It is a
remote client that connects to a daemon you trust (home server, foundation
trust gateway, or self-hosted gateway) via the K.2 TS SDK + a capability
token bound to this device's public key.

## Architecture

| Layer | Tech | Why |
|-------|------|-----|
| App framework | React Native 0.73 + Expo SDK 50 | Single codebase ships iOS .ipa + Android .apk; reuses `@hypermesh/sdk` TypeScript SDK directly; EAS Build handles the toolchain we don't want to babysit. |
| Styling | NativeWind 4 (Tailwind) | Matches `ui/frontend` palette; one mental model across desktop + mobile. |
| Routing | React Navigation 6 (bottom tabs) | Standard, well-supported, minimal boilerplate. |
| Data | TanStack Query 5 | Caching/refetch/refresh-control out of the box. |
| Crypto storage | Expo SecureStore | iOS Keychain / Android Keystore — the platform trust boundary for keys. |
| Auth signing | WebCrypto P-256 placeholder (C.4) → FALCON-1024 via UniFFI (C.4.5) | Real FALCON keygen on phone needs a Rust UniFFI binding. Shape is in place; primitive swaps in C.4.5. |

## Three connection modes (Phase K)

1. **Trust Gateway** — `https://trust.hypermesh.online`. Foundation relay.
   You log in via FALCON device sig; trust issues the token + relays calls
   to your selected target node.
2. **Private Hypermesh** — `https://yourname.hypermesh`. Same flow but the
   gateway is your own private domain (foundation grant from Phase H.1).
3. **Self-hosted** — your own gateway URL, your own TLS cert. Same auth
   handshake.

Mode selection is persisted in SecureStore; re-auth after token expiry
re-uses the same mode.

## Capability-token flow

```
mobile                                gateway                       daemon
  |                                      |                             |
  | -- GET /auth/challenge ------------>|                             |
  | <-- {challenge_hex} -----------------|                             |
  |                                      |                             |
  | sign(challenge) with device key      |                             |
  |                                      |                             |
  | -- POST /auth/create_session ------->|                             |
  |    {device_pubkey, sig, caps, ttl}   |                             |
  |                                      | -- auth.create_session ---->|
  |                                      | <-- CapabilityToken --------|
  | <-- {token, valid_until} -----------|                             |
  |                                      |                             |
  | persist in SecureStore               |                             |
  |                                      |                             |
  | -- any SDK call w/ X-HyperMesh-Capability header --->|             |
  |                                      |                             |
```

On `-32004 CAPABILITY_DENIED` the SDK wrapper wipes the session and the
navigator bounces to `ConnectScreen`.

## Developer setup

> The dev box does not have npm/expo installed by default. C.4 ships
> the source tree; running it requires installing JS tooling.

```bash
# 1. Install Node 18+ and npm/pnpm. Recommended: corepack.
corepack enable
corepack prepare pnpm@9 --activate

# 2. Build the TS SDK first (mobile depends on it via file: protocol).
cd ../sdk/typescript
npm install && npm run build

# 3. Install mobile deps.
cd ../../mobile
npm install

# 4. Type-check.
npx tsc --noEmit

# 5. Run on iOS simulator (requires Xcode + Apple Developer):
npm run ios

# 6. Run on Android emulator (requires Android Studio):
npm run android
```

## Building release artifacts (operator)

Mobile builds use Expo Application Services (EAS). The foundation
operator owns the EAS account + Apple Developer cert + Google Play
signing key — these do **not** live in GitHub Actions secrets.

```bash
# One-time
npm install -g eas-cli
eas login

# Internal-test builds
npm run build:preview               # both platforms

# Store submission builds
npm run build:ios                   # → TestFlight via eas submit
npm run build:android               # → Play Console internal track

# Submit (requires app.json bundleIdentifier + ascAppId in eas.json)
eas submit -p ios --latest
eas submit -p android --latest
```

See `docs/RELEASING.md` "Mobile shell bundles (Phase C.4)" for the full
runbook.

## What's deferred to C.4.5

| Item | Why |
|------|-----|
| FALCON-1024 keygen + signing on device | Needs Rust UniFFI binding (`hypermesh-ffi` → C → JNI/Swift). C.4 ships an ECDSA-P256 placeholder via WebCrypto. |
| `ios/` + `android/` native folders | Auto-generated by `expo prebuild` on first build. C.4 ships only the JS/TS source; native folders materialise when a developer runs `expo prebuild` or `eas build`. |
| Real platform icons | Uses Expo's default. Replace `assets/icon.png`, `splash.png`, `adaptive-icon.png` and re-run `eas build`. |
| Push notifications | Inbox polling for now. Real push requires APNs cert + FCM project. |
| QR-based gateway pairing | Reserved camera permission; UI flow ships C.5. |
| EAS workflow integration in GitHub Actions | Mobile signing keys must not live in CI secrets. Operator-side runbook only. |

## Why React Native + Expo (not native Swift + Kotlin, not Flutter)

1. **Direct SDK reuse.** `@hypermesh/sdk` is TypeScript. RN consumes it
   verbatim — no FFI bridging required for the API client. Native shells
   would each duplicate the SDK in Swift/Kotlin.
2. **Single codebase.** One repo, one TS surface, two stores. Flutter
   would mean re-implementing the SDK in Dart.
3. **Expo abstracts the platform plumbing.** SecureStore, DocumentPicker,
   StatusBar, build pipeline (EAS) — all platform-agnostic. The
   foundation operator deals with Apple/Google account ceremony, not with
   keeping Xcode/Gradle in sync.
4. **The Tauri desktop shell is JS-rendered already.** Same mental model
   carries over.

The only hard cost is the FALCON-1024 binding (C.4.5) — which we'd need
to build for native shells anyway.
